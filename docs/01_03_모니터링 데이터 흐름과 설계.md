
# Zabbix 프로젝트 학습

## 1장 3교시 — 모니터링 데이터 흐름과 설계

### 1. Zabbix 모니터링 동작 흐름

Zabbix는 데이터를 수집하고, 설정한 조건에 따라 장애를 판단한 후 알림을 전송한다.

**핵심 흐름**

Host → Item → Trigger → Event → Action

| 구성요소 | 역할 | 예시 |
|---|---|---|
| Host | 모니터링 대상 | WEB01 |
| Item | 수집할 데이터 항목 | 디스크 사용률 |
| Key | 수집할 데이터 지정 | vfs.fs.size[/,pused] |
| Trigger | 장애 판단 조건 | 디스크 사용률 90% 초과 |
| Event | 장애 발생 등 사건 기록 | 디스크 용량 부족 |
| Action | 이벤트에 따른 작업 | Discord 알림 |

**장애 발생 예시**

1. WEB01에서 디스크 사용률 94% 수집
2. Zabbix Server가 Trigger 조건 평가
3. 90% 초과 조건 충족
4. PROBLEM 이벤트 생성
5. Action에 따라 Discord 알림 전송
6. 운영자가 원인 분석 및 조치
7. 복구 조건 충족 시 정상 상태로 전환

---

### 2. Item과 Key

**Item:** 어떤 데이터를 수집할지 정의하는 항목

**Key:** 해당 Item이 어떤 데이터를 가져올지 지정하는 식별자

| Key | 의미 |
|---|---|
| system.cpu.util | CPU 사용률 |
| system.cpu.load | CPU Load Average |
| vm.memory.size[pavailable] | 사용 가능한 메모리 비율 |
| vfs.fs.size[/,pused] | 루트 디스크 사용률 |
| system.uptime | 서버 가동 시간 |
| net.tcp.service[http] | HTTP 서비스 연결 및 기본 응답 확인 |

**Key 해석 예시**

```text
vfs.fs.size[/,pused]
```

- `vfs.fs.size`: 파일시스템 용량 정보
- `/`: 루트 파일시스템
- `pused`: 사용 중인 공간의 비율(%)

---

### 3. Trigger — 장애 판단 조건

Trigger는 수집한 데이터가 지정된 조건을 만족하는지 평가한다.

**① 최근 측정값 확인**

```text
last(/WEB01/vfs.fs.size[/,pused])>90
```

WEB01의 가장 최근 디스크 사용률이 90%를 초과하면 장애로 판단한다.

**② 최근 5분 평균 확인**

```text
avg(/WEB01/vfs.fs.size[/,pused],5m)>90
```

최근 5분간 수집된 디스크 사용률의 평균이 90%를 초과하면 장애로 판단한다.

**③ 최근 5분 최솟값 확인**

```text
min(/WEB01/vfs.fs.size[/,pused],5m)>90
```

최근 5분 동안 수집된 모든 값이 90%를 초과한 경우 조건을 만족한다.

| 함수 | 의미 |
|---|---|
| last() | 가장 최근 측정값 |
| avg() | 지정 기간 평균값 |
| min() | 지정 기간 최솟값 |
| max() | 지정 기간 최댓값 |

**주의:** min(5m)은 5분 동안 수집된 값들을 평가하는 것이며, 모든 순간을 연속 측정한다는 뜻은 아니다.

### 4. Event와 Action

**Event**
- Trigger의 상태 변화 등에 따라 생성되는 사건 기록
- 장애 발생 및 복구 이력을 관리하는 데 사용

**Action**
- 이벤트 발생 시 실행할 작업 정의
- Discord 또는 이메일 알림 전송
- 조건에 따른 알림 대상 및 동작 설정

**장애 처리 과정**

```text
정상 상태 (OK)
      ↓
임계치 초과
      ↓
Trigger 조건 충족
      ↓
PROBLEM 이벤트 발생
      ↓
Action → Discord 장애 알림
      ↓
운영자 원인 분석 및 조치
      ↓
복구 조건 충족
      ↓
정상 상태 (OK)
      ↓
설정된 경우 복구 알림 전송
```

**알림 플래핑(Alert Flapping)**

측정값이 임계치 주변에서 반복적으로 변하면 장애 발생과 복구 알림이 계속 반복될 수 있다.

해결 방법:
- 일정 기간 평균값 사용
- 장애 및 복구 임계치를 다르게 설정
- 알림 조건과 심각도 조정

---

### 5. 데이터 수집 주기

Zabbix는 Item마다 데이터 수집 주기를 지정할 수 있다.

| 수집 주기 | 특징 |
|---|---|
| 10초 | 빠른 탐지, 높은 수집 부하 |
| 30초 | 비교적 세밀한 관찰 |
| 1분 | 일반적인 실습에 적합 |
| 5분 | 낮은 수집 부하, 탐지 지연 가능 |

**수집 주기가 너무 짧으면**
- Server 처리 부하 증가
- 네트워크 통신량 증가
- Database 저장 데이터 증가

따라서 지표의 중요도와 특성에 맞게 수집 주기를 설정해야 한다.

### 6. History와 Trends

| 구분 | History | Trends |
|---|---|---|
| 의미 | 개별 수집값 저장 | 시간별 집계 데이터 |
| 저장 내용 | 원래 측정값 | 최솟값·최댓값·평균·개수 |
| 활용 | 상세 장애 분석 | 장기적인 추세 분석 |
| 저장 용량 | 상대적으로 큼 | 상대적으로 작음 |

**핵심**
- History: 과거 개별 측정값 확인
- Trends: 장기간 자원 사용 추세 확인

숫자형 Item은 Trends로 집계할 수 있으며, 데이터 보관 기간을 적절하게 설정해야 DB 용량을 관리할 수 있다.

### 7. Marble 프로젝트 모니터링 설계

**① WEB 서버**
- CPU / Memory / Disk
- Apache 서비스 상태
- HTTP 상태코드
- HTTP 응답 시간

**② WAS 서버**
- CPU / Memory / Disk
- Java 프로세스 상태
- TCP 8080 포트
- Spring Boot `/health`
- DB 연결 상태 `/health/db`
- HTTP 응답 시간

**③ DB 서버**
- CPU / Memory / Disk
- MySQL 서비스 상태
- TCP 3306 포트
- 실제 DB 접속 가능 여부
- Primary/Replica 복제 상태 및 지연

**모니터링 설정 예시**

| 대상 | 지표 | 수집 주기 | 장애 조건 |
|---|---|---|---|
| 공통 | CPU | 1분 | 5분 평균 90% 초과 |
| 공통 | Disk | 1분 | 80% 초과 |
| WEB | HTTP | 1분 | 연속 응답 실패 |
| WAS | /health | 30초 | 연속 응답 실패 |
| DB | MySQL | 1분 | 연속 접속 실패 |

※ 임계치와 수집 주기는 학습용 예시이며 실제 운영 환경에 맞게 조정한다.

**중요:** 서버가 정상이어도 애플리케이션에 장애가 발생할 수 있으므로 서버 자원과 서비스 가용성을 함께 모니터링해야 한다.

### 8. Linux 기초 모니터링 실습

```bash
# 디스크 사용률 확인
df -h /

# 디스크 사용률 숫자 추출
df -P / | awk 'NR==2 {gsub(/%/, "", $5); print $5}'

# CPU 및 프로세스 확인
top

# 메모리 사용량 확인
free -h

# 서비스 상태 확인
systemctl status apache2

# 웹 서비스 응답 확인
curl -I http://localhost
```

**실습 개념 연결**

- `df`: Item에 해당하는 데이터 수집
- 수집값과 임계치 비교: Trigger 평가
- 조건 충족 시 로그 생성: Event 모의 구현
- 알림 메시지 출력: Action 모의 구현

### 9. 장애 대응 핵심

**상황: Zabbix에서 CPU 사용률 데이터가 갱신되지 않음**

가능한 원인:
1. Zabbix Agent 서비스 중지
2. 네트워크 통신 장애
3. 방화벽 차단
4. Item Key 설정 오류
5. 데이터 수집 주기 문제

**확인 명령어**

```bash
# Agent 실행 상태
sudo systemctl status zabbix-agent2

# 포트 확인
sudo ss -lntp

# IP 확인
ip -br addr

# Agent 로그 확인
sudo journalctl -u zabbix-agent2 -n 50 --no-pager
```

※ Agent 설치 이후 실행한다.

**중요:** 데이터가 수집되지 않는 것과 측정값이 0인 것은 다르다.

데이터 미수집 여부는 `nodata()` 등의 별도 조건으로 감시할 수 있다.

### 10. 면접 예상 질문

**Q1. Zabbix는 어떻게 장애를 탐지하나요?**

Zabbix는 Item을 통해 데이터를 수집하고, Server가 Trigger 조건을 평가합니다.

조건을 충족하면 장애 이벤트가 생성되고, 설정된 Action에 따라 Discord나 이메일로 알림을 보냅니다.

**Q2. 수집 주기를 짧게 설정하면 무조건 좋은가요?**

수집 주기가 짧으면 장애 탐지에 유리하지만 Server와 Database의 부하가 증가할 수 있습니다.

따라서 데이터의 중요도와 변경 빈도를 고려하여 적절한 수집 주기를 설정해야 합니다.

**Q3. 서버 상태가 정상이어도 서비스 장애가 발생할 수 있나요?**

네. CPU나 메모리 상태가 정상이어도 애플리케이션이 종료되거나 DB 연결이 실패할 수 있습니다.

따라서 서버 자원 모니터링과 HTTP 헬스체크 같은 서비스 모니터링을 함께 구성해야 합니다.

### 11. 핵심 암기 포인트

1. Host = 모니터링 대상
2. Item = 수집할 데이터 항목
3. Key = 수집할 데이터 식별자
4. Trigger = 장애 판단 조건
5. Event = 장애 발생·복구 등의 사건 기록
6. Action = 알림 및 작업 실행
7. History = 개별 측정값 저장
8. Trends = 장기 집계 데이터
9. 수집 주기는 정확성과 부하를 고려하여 설정
10. 서버 자원과 애플리케이션 상태를 함께 모니터링

**가장 중요한 흐름**

Host → Item → Trigger → Event → Action

WEB01 → 디스크 사용률 → 90% 초과 → 장애 발생 → Discord 알림
